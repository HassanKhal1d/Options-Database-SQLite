## About This Project

This repository contains the capstone project for the **Database Management for Trading: Basic** course, completed as part of the **Algo Trading for Beginners** learning track on Quantra by QuantInsti.

The course spans 27 sections covering the full lifecycle of trading data management — from understanding market data structure and database fundamentals, through schema design, data insertion, and querying, to options chain sourcing, cleaning, and storage. This capstone project, introduced in **Section 20**, consolidates the practical skills developed across the preceding sections — most directly Sections 15 through 19, which cover the structure, sourcing, filtering, and storage of options chain data.

The project builds an end-to-end data engineering pipeline for high-frequency SPX options data: loading and cleaning 1-minute interval CSV files, applying liquidity and strike-distance filters, storing the results in a structured SQLite database with separate call and put tables, and querying the database to extract intraday and expiry-based data slices relevant to options trading strategy research.

## Notebook 1 — Data Acquisition & Preprocessing

**File:** `01_Data_Acquisition_Preprocessing.ipynb`

Loads all `SPX_minute_options_2023-10-*.csv` files dynamically from the `data_modules` directory, concatenates them into a single DataFrame, and performs all cleaning and type standardisation steps required before filtering.

**Steps performed:**

**1. Dynamic file loading**
All CSVs matching the `SPX_minute_options_2023-10-` prefix are discovered at runtime using `os.listdir()` and loaded in a single loop, making the pipeline robust to additional data files being added to the directory.

**2. Column name standardisation**
Raw column names arrive enclosed in square brackets (e.g. `[QUOTE_DATETIME]`). These are cleaned by stripping leading and trailing whitespace using `.str.lstrip()` / `.str.rstrip()`, then removing the square brackets with `.str.strip('[]')`. The result is clean, lowercase column names such as `quote_datetime`, `strike`, `c_delta`.

**3. Datetime index**
`quote_date` is converted to a proper datetime and set as the DataFrame index, making the dataset time-indexed for date-based slicing throughout subsequent notebooks. The index name is removed for cleanliness.

**4. Redundant column removal**
`quote_date`, `quote_datetime`, and `quote_time` are dropped after the index is set — the index carries the date information and these columns become redundant.

**5. String whitespace cleanup**
A defensive `.applymap()` pass strips leading and trailing whitespace from all string-type values, guarding against any invisible formatting inconsistencies in the raw files.

**6. Type enforcement**
Numeric columns are identified programmatically by prefix pattern: all `c_` and `p_` columns (excluding `c_size` and `p_size`, which are strings in `"N x N"` format) are cast to numeric using `pd.to_numeric()`. Date columns containing `"date"` in their name are converted using `pd.to_datetime()`.

**Output:** `options_data_raw_cleaned.csv`

## Notebook 2 — Data Filtering

**File:** `02_Data_Filtering.ipynb`

Applies five sequential filters to remove illiquid and unreliable contracts, adds derived mid-price and spread columns, then separates the combined dataset into dedicated call and put DataFrames.

**Filters applied (in order):**

| # | Filter | Logic | Rationale |
|---|---|---|---|
| 1 | **Market depth** | Remove rows where `c_size == '0 x 0'` or `p_size == '0 x 0'` | No available bids or asks — contract has no market depth |
| 2 | **Strike distance** | Keep rows where `strike_distance_pct <= 0.05` | Retains only strikes within 5% of the underlying price, focusing on relevant near-the-money contracts |
| 3 | **Contract value** | Keep rows where `c_last > 0` and `p_last > 0` | Removes contracts with no last-traded price — indicative of inactive or stale contracts |
| 4 | **Implied volatility** | Drop rows where `c_iv` or `p_iv` is NaN | Ensures all retained contracts have a valid implied volatility reading |
| 5 | **Bid/ask validity** | Remove rows where `c_bid`, `p_bid`, `c_ask`, or `p_ask` equal zero | Ensures only contracts with live, valid two-sided quotes are retained |

**Derived columns added:**

| Column | Formula | Purpose |
|---|---|---|
| `c_mid` | `(c_bid + c_ask) / 2` | Mid-price of the call — used as a fair-value estimate |
| `p_mid` | `(p_bid + p_ask) / 2` | Mid-price of the put |
| `c_spread` | `c_ask - c_bid` | Absolute bid-ask spread of the call — proxy for transaction cost |
| `p_spread` | `p_ask - p_bid` | Absolute bid-ask spread of the put |

**Call / Put separation:**

The filtered DataFrame is split into two separate DataFrames:

- `call_options_data` — common columns + all `c_` prefixed columns
- `put_options_data` — common columns + all `p_` prefixed columns

Common columns retained in both: `symbol`, `underlying_last`, `expire_date`, `expiry_type`, `dte`, `strike`, `strike_distance`, `strike_distance_pct`

**Output:** `call_options_data.csv`, `put_options_data.csv`

## Notebook 3 — SQL Database Design & Implementation

**File:** `03_SQL_Database_Design_Implementation.ipynb`

Designs and implements a SQLite database using SQLAlchemy, structured in two phases: a design-and-test phase to validate the schema before deployment, and a production ETL phase with reusable, modular functions.

### Phase 1 — Design & Testing Schema

**1.1 Logger setup**
A Python `logging` handler is configured at `INFO` level with timestamps, providing a transparent audit trail of every database operation during development.

**1.2 Database configuration & PRAGMA settings**
The SQLite database is created via SQLAlchemy's `create_engine()`. Three PRAGMA settings are applied on connection to optimise performance and data integrity:

| PRAGMA | Value | Effect |
|---|---|---|
| `foreign_keys` | `ON` | Enforces referential integrity constraints |
| `journal_mode` | `WAL` | Write-Ahead Logging — improves concurrent read/write performance |
| `synchronous` | `NORMAL` | Reduces disk I/O overhead while maintaining reasonable durability |

**1.3 Table schema**
Two tables are defined with explicit column types and constraints:

```sql
CREATE TABLE IF NOT EXISTS call_options_data (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    quote_date          TEXT    NOT NULL,
    symbol              TEXT    NOT NULL,
    underlying_last     REAL    NOT NULL,
    expire_date         TEXT    NOT NULL,
    expiry_type         TEXT,
    dte                 REAL,
    strike              REAL    NOT NULL,
    strike_distance     REAL,
    strike_distance_pct REAL,
    c_delta             REAL,
    c_gamma             REAL,
    c_vega              REAL,
    c_theta             REAL,
    c_rho               REAL,
    c_iv                REAL,
    c_volume            INTEGER,
    c_last              REAL,
    c_bid               REAL,
    c_ask               REAL,
    c_mid               REAL,
    c_spread            REAL
);
```

An identical structure is used for `put_options_data` with `p_` prefixed Greek and pricing columns.

**1.4 Indexes**
Indexes are created on the most frequently queried columns to optimise lookup performance:

```sql
CREATE INDEX IF NOT EXISTS idx_call_symbol     ON call_options_data (symbol);
CREATE INDEX IF NOT EXISTS idx_call_quote_date ON call_options_data (quote_date);
CREATE INDEX IF NOT EXISTS idx_call_strike     ON call_options_data (strike);
CREATE INDEX IF NOT EXISTS idx_call_expire     ON call_options_data (expire_date);
```

Equivalent indexes are created on the `put_options_data` table.

**1.5 Staging tables**
Data is first written to temporary staging tables (`staging_call_options_data`, `staging_put_options_data`) using `df.to_sql(..., if_exists='replace')`. This separates incoming data from the production table during validation.

**1.6 Deduplication & insertion**
Before final insertion, a `DELETE` statement removes any rows from the staging table that already exist in the main table, matched on `symbol`, `quote_date`, `expire_date`, and `strike`. This prevents duplicate records on repeated pipeline runs. Clean records are then inserted from staging into the main table.

### Phase 2 — Production ETL Pipeline

The design-and-test logic is refactored into two modular, reusable functions:

**`create_table(option_type, option_type_prefix)`**
Creates the main table and its indexes if they do not already exist. Accepts `"call"` or `"put"` and the corresponding column prefix `"c"` or `"p"` to generate the correct schema dynamically.

**`process_option_data(option_type, option_type_prefix, df)`**
Orchestrates the full ingestion workflow: calls `create_table()`, writes the incoming DataFrame to the staging table, runs deduplication, inserts clean records into the main table, and drops the staging table on completion.

**Running the pipeline:**
```python
process_option_data("call", "c", call_options_data)
process_option_data("put",  "p", put_options_data)
```

**Output:** `options_data.db` — a structured SQLite database with `call_options_data` and `put_options_data` tables, indexed and deduplicated, ready for querying.

## Notebook 4 — Data Querying & Retrieval

**File:** `04_Data_Querying_Retrieval.ipynb`

Implements a set of SQL queries against the SQLite database using SQLAlchemy's `text()` for parameterised queries and `pd.read_sql()` to load results directly into DataFrames for analysis and visualisation.

### Queries Implemented

**Full table retrieval**
```sql
SELECT * FROM call_options_data;
SELECT * FROM put_options_data;
```

**Date-filtered retrieval (parameterised)**
```sql
SELECT * FROM call_options_data WHERE quote_date = :date;
SELECT * FROM put_options_data  WHERE quote_date = :date;
```
Uses SQLAlchemy's `text()` with bound parameters to prevent SQL injection and allow clean reuse with different dates.

**Gamma Scalping candidates**
```sql
SELECT * FROM call_options_data
WHERE symbol = :symbol
  AND ABS(strike_distance) <= 15
  AND quote_date = :date
  AND c_gamma >= 0.0004
  AND c_iv >= 0.50
  AND dte <= 3
ORDER BY expire_date, strike;
```
Targets near-the-money, high-gamma, short-dated calls. An equivalent query runs on the put table with `p_gamma >= 0.0003` and `strike_distance <= 20`.

> **Finding:** SPX is not suitable for gamma scalping. As a large-cap index with no earnings-style catalyst events, SPX gamma values are too low and IV is insufficiently volatile to support a scalping strategy on this dataset.

**IV Crush candidates**
```sql
SELECT * FROM call_options_data
WHERE symbol = :symbol
  AND quote_date = :date
  AND c_iv >= 0.7
  AND c_volume >= 20
ORDER BY expire_date, strike;
```
Screens for high-IV, liquid contracts that could be candidates for selling into an anticipated IV contraction.

> **Finding:** IV Crush is not the appropriate strategy for SPX options. SPX has no earnings-style catalysts; IV in this dataset is extremely stable in the 0.70–0.85 range; the dataset is dominated by 0DTE contracts; and deep OTM skew — not event risk — drives the observed IV levels. Bid-ask spreads are also too wide relative to the potential premium collected.

### IV Crush Analysis — Visualisations

The following charts are generated for both call and put crush candidates:

| Chart | Purpose |
|---|---|
| IV distribution histogram (KDE) | Visualises the spread and concentration of implied volatility across candidates |
| Volume vs IV scatter (size = spread, colour = DTE) | Shows the relationship between liquidity and opportunity; larger points indicate wider spreads |
| IV vs Strike Distance scatter (colour = DTE) | Identifies whether high-IV contracts cluster near or away from the money |
| IV vs Delta scatter (colour = DTE) | Maps the risk profile of candidates across the delta spectrum |
| Bid-ask spread histogram | Assesses tradeability — wide spreads reduce the viability of premium-selling strategies |
| DTE vs IV scatter | Examines term structure — whether short-dated or longer-dated contracts carry higher IV |

### IV Crush Score

A composite ranking metric is computed to rank candidates by overall attractiveness:

```python
crush_score = (iv * 0.6) + (volume.rank(pct=True) * 0.3) - (spread.rank(pct=True) * 0.1)
```

This weights implied volatility most heavily (60%), rewards high volume as a liquidity signal (30%), and penalises wide bid-ask spreads (10%). Results are sorted descending to surface the highest-scoring contracts.

## Key Design Decisions

**Why SQLAlchemy over raw `sqlite3`?**
SQLAlchemy provides a clean abstraction over the database connection, enables parameterised queries via `text()` to guard against injection, and integrates directly with pandas via `to_sql()` and `read_sql()` — reducing boilerplate for a data-heavy pipeline.

**Why WAL journal mode?**
Write-Ahead Logging allows reads and writes to proceed concurrently without locking the entire database file. For a pipeline that reads from the database while writing staging data, this prevents contention.

**Why staging tables for insertion?**
Writing to a staging table first allows deduplication to be performed as a SQL operation before any data touches the main table. This keeps the main tables clean on every run and makes the pipeline safe to re-execute without accumulating duplicate rows.

**Why separate call and put tables rather than a single table with an `option_type` column?**
Separating calls and puts eliminates the need for a `WHERE option_type = 'call'` filter on every query, halves the rows scanned per query, and keeps the column naming clean — each table uses unprefixed Greek and pricing column names (`delta`, `gamma` etc.) rather than `c_delta` / `p_delta`, which would be needed in a combined table to avoid ambiguity.

## Strategy Research Findings

| Strategy | Tested On | Conclusion |
|---|---|---|
| Gamma Scalping | SPX calls and puts, 2023-10-02 | Not suitable — gamma values too low, no sufficient intraday vol to scalp |
| IV Crush | SPX calls and puts, 2023-10-03 | Not suitable — SPX has no event-driven IV spikes; IV is structurally stable; spreads too wide |

These findings are not generalisable beyond this two-day dataset but illustrate how the querying infrastructure can be used to screen and evaluate options strategies systematically.

## Limitations

- **Temporal scope:** Two trading days are insufficient for strategy validation or robust threshold calibration. All findings are illustrative, not statistically significant.
- **No tick data:** Volume figures are cumulative intraday snapshots, not confirmed trade executions. Liquidity assessments reflect quoted depth, not realised transaction costs.
- **Fixed strike range:** The 4,100–4,500 strike range covers only the near-the-money portion of the full SPX chain. Deep ITM and far OTM dynamics are not represented.
- **Static dataset:** The pipeline is designed for batch ingestion of pre-formed CSV files. It does not connect to a live data feed or support real-time updates.
